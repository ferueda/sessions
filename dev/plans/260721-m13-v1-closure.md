# Release standalone Sessions and close V1

## Goal

Complete M13.3 with standalone Sessions as the only product and integration
boundary. The CLI is installed from npm and the matching `sessions` Agent Skill
is installed directly from the same immutable Sessions release into each local
agent host. No Sessions wrapper, package pin, vendored snapshot, cache, or
rollback route belongs in the Harness repository. The frozen Harness baseline
remains historical M13.1 comparison evidence only.

V1 is complete when the authoritative docs reflect that boundary, Release
Please publishes the already-proposed `0.2.0` release through the protected
qualification workflow, the exact registry CLI and same-tag local skill are
verified, the final artifact evidence is recorded, and the completed V1 roadmap
and executor plan are removed.

## Changes

1. `docs/architecture-memo.md`, `docs/decisions/README.md`,
   `docs/decisions/0005-keep-one-way-ownership-with-harness.md`, a replacement
   standalone-installation ADR, `test/docs-contracts.test.ts`,
   `dev/plans/260713-v1-implementation-roadmap.md`, and
   `docs/contributing/v1-acceptance.md` — supersede the planned Harness wrapper
   with the accepted standalone installation boundary. Remove M13.2 as a gate,
   preserve the immutable legacy comparison as history, and make M13.3 the only
   remaining milestone. State that host discovery, copying, upgrades, and
   removal belong to the external skill installer and local user state; the
   Sessions repository owns the packaged skill and matching release tags. Do
   not modify Harness or treat this repository's `harness.json` review-tool
   configuration as product integration. Follow the ADR supersession contract
   by linking both decisions, and lock the resulting boundary in the focused
   documentation contract.

2. `dev/plans/README.md` — publish this plan as the sole active executor plan.
   Run `pnpm check:docs`, `pnpm check`, and the full change-review workflow for
   the pre-release alignment change before publication proceeds.

3. Release Please PR `#57` and `.github/workflows/release.yml` — after the
   alignment change is merged, review the generated `0.2.0` version, changelog,
   and public version markers, then merge the automation-owned release PR. Do
   not hand-edit version files, tags, or release commits. Require the exact
   release revision to pass `pnpm check`, one-tarball Linux/macOS/Windows smoke,
   immutable tag and GitHub release creation, protected npm publication,
   registry integrity/latest/install checks, signatures, and SLSA provenance.
   Stop for user action only if the protected `npm` environment needs approval
   or the existing documented retry path is required.

4. Published `@ferueda/sessions@0.2.0` and tag `v0.2.0` — verify registry and
   GitHub state after the release workflow succeeds. Install or upgrade the
   local CLI and copied Agent Skill from that exact version/tag using the
   documented external installer with telemetry disabled, then verify
   `sessions --version`, read-only `doctor` and `paths`, the local skill lock's
   `ferueda/sessions` source and `v0.2.0` ref, and exact ten-file skill equality
   with the release. Indexing remains a separate permission and is not part of
   release verification.

5. `docs/contributing/v1-acceptance.md`, `docs/architecture-memo.md`,
   `docs/project-intent.md`, and `dev/plans/README.md` — record the final tag,
   release commit, qualified artifact digest/integrity, registry/provenance
   result, and matching local skill verification. Mark V1 current and complete,
   remove `dev/plans/260713-v1-implementation-roadmap.md` and this executor plan,
   and leave no active V1 plan. Run `pnpm check` and full change review on the
   closeout diff.

## Verify

- Pre-release alignment and post-release closeout each pass `pnpm check` and the
  full `change-review` workflow.
- The protected Release workflow succeeds for the immutable `v0.2.0` release
  revision, including all three operating-system smokes and registry provenance
  checks.
- Public npm `latest`, installed CLI version, immutable skill tag, local skill
  lock, and exact skill tree all agree on `0.2.0`.

## Boundaries

- Do not change or open a pull request in Harness; do not restore its removed
  implementation or add a wrapper, package pin, cache, vendored snapshot, or
  rollback path there.
- Do not index provider history, delete Sessions data, publish manually, move a
  release tag, or bypass the protected npm environment.
- Do not claim V1 release completion or remove the roadmap before the registry
  and locally installed matching skill are verified from the published bytes.
